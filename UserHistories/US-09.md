### 1. User Story
**Como** Sistema
**Quiero** evaluar la fecha y hora del servidor frente a las reglas de cierre
**Para** restringir cambios fuera de término en la interfaz del cliente.

### 2. Descripción de la Funcionalidad (Flow)
1. Esta historia actúa principalmente a nivel de **Middleware y Helpers**.
2. Cada vez que el frontend pide el estado de un día (`GET available-menus`) o el usuario intenta enviar un pedido (`POST` o `PUT` de Order en **US-08**), el sistema evalúa:
   - ¿Qué día se quiere pedir? (Ej: Martes).
   - Verifica la hora y fecha actual del Servidor (`moment()` o `dayjs()`).
   - Aplica la Regla General (Ej: si son pasadas las 20:00 del Lunes, se bloquea el Martes).
   - Si el día es Lunes o posterior a un Feriado, aplica la regla especial de la **US-06**.
3. El frontend marca visualmente la UI con candados o el texto "Cerrado".
4. Si un usuario intenta "hackear" enviando un POST directo con un payload, el backend rechaza con un error 403 Forbidden o 400 Bad Request, indicando que el horario de corte caducó.

### 4. Estructura de Endpoints y URLs
*   Aplica a validaciones de los endpoints de la US-08 (`POST /api/users/me/orders`, `PUT /api/users/me/orders/:id`).

- **Error de Horario de Corte (403 Forbidden)**:
```json
{
  "success": false,
  "message": "El horario límite para realizar o modificar pedidos para esta fecha ha caducado.",
  "code": "CUTOFF_EXCEEDED"
}
```
