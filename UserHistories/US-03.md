### 1. User Story
**Como** Usuario Nuevo
**Quiero** registrar mis datos personales en la aplicación
**Para** comenzar a operar como cliente particular o corporativo.

### 2. Descripción de la Funcionalidad (Flow)
#### Flujo de Registro (Onboarding):
1. El usuario ingresa a la pantalla de Registro y escribe su Email.
2. Al perder el foco del input de email (o hacer siguiente), el frontend consulta si el email está pre-asignado a una empresa (configurado en **US-02**).
3. **Camino A (Email Corporativo)**:
   - Si está asignado, los campos "Empresa" y "Tipo de Menú" se muestran pre-cargados y bloqueados.
   - El backend creará automáticamente la primera dirección apuntando a la empresa.
4. **Camino B (Email Particular)**:
   - Si no está asignado, esos campos se ocultan o quedan libres como Usuario Particular.
5. El usuario completa los datos obligatorios: Nombre, Apellido, Teléfono, DNI, y contraseña. Además de ingresar su primera Dirección de Entrega. Si es un usuario corporativo y la empresa carece de dirección física, se exigirá obligatoriamente una dirección personalizada.
6. Envía el formulario. El backend registra al usuario en estado inactivo (`isVerified: false`) y despacha un correo con un código OTP de 6 dígitos.
7. El usuario es redirigido a la pantalla de validación, ingresa el OTP. El backend valida el código y finalmente devuelve el token de sesión.

### 3. Lista Completa de Campos
*   `email`: String (email).
*   `password`: String (min 8 chars).
*   `firstName`: String.
*   `lastName`: String.
*   `phone`: String.
*   `dni`: String.
*   `address`: Objeto (street, number, locality, reference).

## Enhanced

### 1. Descripción de la Funcionalidad (Flow) Detallada

#### 1.1 Validación de Email (Pre-check)
1. El usuario introduce su email en el formulario de registro.
2. Al perder el foco (`onBlur`) o tras presionar "Siguiente", el frontend realiza un `POST` a `/api/auth/check-email`.
3. **Escenario 1 (Email ya registrado)**:
   - Si el email ya pertenece a un usuario en la tabla `users`, el backend responde con un error `400 Bad Request` indicando que el correo electrónico ya está registrado. El frontend muestra un mensaje de error solicitando iniciar sesión.
4. **Escenario 2 (Email corporativo pre-asignado)**:
   - El backend busca en `company_employees` si existe una fila con ese email y `status = 'pending'`.
   - Si existe, se obtiene el `companyId` y se consulta la tabla `companies` para verificar que `isActive = true`.
   - **Sub-caso 2.1 (Empresa Activa)**: El backend devuelve `isCorporate: true`, el nombre de la empresa, el tipo de beneficio, y si permite direcciones extra (`allowExtraAddresses`). El frontend pre-carga estos datos, bloquea los campos corporativos y ajusta la sección de direcciones.
   - **Sub-caso 2.2 (Empresa Inactiva)**: Se trata como un email particular (Camino B), pero registrando logs de advertencia.
5. **Escenario 3 (Email particular)**:
   - Si no hay coincidencias en `company_employees`, el backend devuelve `isCorporate: false`. El formulario habilita la sección para ingresar la dirección de entrega obligatoria y oculta los campos de beneficio corporativo.

#### 1.2 Registro y Creación de Cuenta
El usuario envía el formulario con todos los campos obligatorios. El backend procesa el registro de manera atómica (mediante una transacción de base de datos):
1. **Validación de Datos**: Se ejecutan validaciones estrictas del lado del servidor (formato de email, longitud de contraseña, unicidad de DNI y email, formato de teléfono, etc.).
2. **Encriptación**: Se genera el hash de la contraseña usando `bcrypt` (10 rondas).
3. **Creación del Usuario**: Se crea el registro en `users` con el rol predeterminado `user`. Si es corporativo, se asocia su `companyId`.
4. **Vinculación Corporativa (Transaccional)**:
   - Si es corporativo, se actualiza el registro en `company_employees` cambiando su `status` a `'registered'` y asociando el `userId` recién creado.
5. **Creación de Dirección (Transaccional)**:
   - **Caso Particular o Corporativo con Dirección Extra provista**: Se crea el registro en la tabla `addresses` vinculando el `userId` y marcándolo como `isDefault = true`.
   - **Caso Corporativo (Sin dirección extra)**: Se crea una dirección para el usuario copiando los datos de la dirección física de la empresa (`street`, `addressNumber` como `number`, `locality`, y la referencia "Dirección Corporativa").
6. **Despacho de OTP**: Tras registrar con éxito la transacción, el backend genera un código OTP de 6 dígitos, lo asocia al usuario (`otpCode`) y lo despacha por correo electrónico. El endpoint devuelve un código 201 sin establecer sesión.
7. **Verificación de Email**: El usuario ingresa a la vista de verificación (`/verify-email`), proporciona el código, y si es válido se marca la cuenta como `isVerified = true`, se limpia el `otpCode` y recién entonces se emite la cookie `HttpOnly` con el JWT para iniciar la sesión.

- `reference`?: string (opcional)

- `dni` (DataTypes.STRING, allowNull: false, unique: true)

Estructura de la tabla `addresses`:
- `id`: DataTypes.INTEGER, autoIncrement, primaryKey
- `userId`: DataTypes.INTEGER, allowNull: false, references: { model: 'users', key: 'id' }, onDelete: 'CASCADE'

- `number`: DataTypes.STRING, allowNull: false
- `locality`: DataTypes.STRING, allowNull: false
- `reference`: DataTypes.STRING, allowNull: true
- `isDefault`: DataTypes.BOOLEAN, allowNull: false, defaultValue: true

### 3. Estructura de Endpoints y URLs

#### 3.1 Verificar pre-asignación: `POST /api/auth/check-email`
- **Request Body**:
```json
{
  "email": "juan@acme.com"
}
```
- **Responses**:
  - **200 OK (Email Corporativo Pre-asignado)**:
    ```json
    {
      "success": true,
      "message": "Email is pre-assigned to a company",
      "data": {
        "isCorporate": true,
        "companyId": 1,
        "companyName": "ACME S.A.",
        "benefitType": "Corporativo Premium",
        "allowExtraAddresses": false
      }
    }
    ```
  - **200 OK (Email Particular)**:
    ```json
    {
      "success": true,
      "message": "Email is not pre-assigned",
      "data": {
        "isCorporate": false,
        "companyId": null,
        "companyName": null,
        "benefitType": null,
        "allowExtraAddresses": false
      }
    }
    ```
  - **400 Bad Request (Email Inválido o ya registrado)**:
    ```json
    {
      "success": false,
      "message": "Email is already registered"
    }
    ```

#### 3.2 Registro: `POST /api/auth/register`
- **Request Body**:
```json
{
  "email": "juan@acme.com",
  "password": "securepassword123",
  "firstName": "Juan",
  "lastName": "Pérez",
  "phone": "3815555555",
  "dni": "30123456",
  "address": {
    "street": "San Martín",
    "number": "123",
    "locality": "Lules",
    "reference": "Oficina central"
  }
}
```
*Nota: El objeto `address` es opcional en la petición solo si `check-email` determinó que es corporativo y `allowExtraAddresses` es falso.*

- **Responses**:
  - **201 Created (Registro Exitoso)**:
    ```json
    {
      "success": true,
      "message": "Verification required",
      "data": {
        "user": {
          "id": 15,
          "email": "juan@acme.com",
          "name": "Juan Pérez",
          "role": "user",
          "companyId": 1
        }
      }
    }
    ```
    *Nota: No establece sesión, el frontend debe redirigir a verificación.*

#### 3.3 Verificar Email: `POST /api/auth/verify-email`
- **Request Body**:
```json
{
  "email": "juan@acme.com",
  "code": "123456"
}
```
- **200 OK (Verificación Exitosa)**:
    ```json
    {
      "success": true,
      "message": "Email verified successfully",
      "data": { "user": { ... } }
    }
    ```
    *Establece la cookie `token` (HttpOnly, Secure, SameSite=Strict).*
  - **400 Bad Request (Fallas de Validación o campos duplicados)**:
    ```json
    {
      "success": false,
      "message": "DNI is already registered",
      "data": null
    }
    ```

### 6. Requerimientos No Funcionales

#### 6.1 Seguridad
- **Password Hashing**: Uso de `bcrypt` (10 rounds) al crear el usuario.
- **Rate Limiting**: Aplicación de `authLimiter` en `/check-email` y `/register` para prevenir ataques de denegación de servicio (DoS) y fuerza bruta.
- **Validación estricta**: Uso de Zod en el backend para validar todos los tipos, longitudes y formatos de datos del `payload`.
- **Sesión segura**: Almacenamiento de tokens JWT mediante cookies `HttpOnly`, `Secure` (en producción), y `SameSite: 'strict'` para mitigar ataques XSS y CSRF.

#### 6.2 Concurrencia e Integridad
- Uso obligado de transacciones (`sequelize.transaction()`) al guardar al usuario, su dirección, y actualizar el estado de vinculación corporativa. Esto evita estados inconsistentes si ocurre un error intermedio.

#### 6.3 Rendimiento
- Creación de índices de base de datos para los campos `email` y `dni` en la tabla `users` para garantizar consultas veloces.
- Índice en el campo `email` de `company_employees`.
